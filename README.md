# watch-together-server

**Watch Together** — комната для совместного просмотра фильмов и видео-контента.

Сервис для совместного просмотра видео с возможностью синхронизации и управления
просмотром несколькими пользователями в реальном времени.

**Стек технологий:** Python, FastAPI, Uvicorn, PostgreSQL, SQLAlchemy 2, WebSocket, Pytest.

## 1. Обзор

Пользователь создаёт «комнату», задаёт источник видео и приглашает участников по ссылке.
Все участники видят одно и то же видео в одной и той же позиции: пауза, перемотка и смена
скорости применяются одновременно у всех. Рядом с плеером находится чат, позволяющий
обсуждать происходящее на экране.

Серверная часть (данный репозиторий) отвечает за:

- управление пользователями, комнатами и членством в них;
- хранение и рассылку состояния воспроизведения;
- обмен сообщениями чата;
- контроль прав на управление просмотром;
- синхронизацию клиентов с учётом сетевых задержек.

Клиентская часть (плеер) разрабатывается отдельно и взаимодействует с сервером
по REST API и WebSocket.

## 2. Проблема и мотивация

Существующие решения (Teleparty, Syncplay и др.) либо привязаны к конкретному
видеохостингу, либо требуют установки настольного клиента, либо не дают гибкого
управления правами. Учебная задача проекта — реализовать собственный сервер
совместного просмотра с понятной архитектурой, честной синхронизацией состояния и
покрытием тестами, отработав при этом ключевые темы: асинхронный FastAPI,
WebSocket-соединения, работу с PostgreSQL через SQLAlchemy 2.0 и проектирование API.

## 3. Цели и границы

### 3.1. Цели

1. Реализовать серверную часть с полным жизненным циклом комнаты: создание,
   присоединение, просмотр, закрытие.
2. Обеспечить синхронизацию состояния плеера между участниками с расхождением
   не более 1 секунды.
3. Реализовать чат с доставкой сообщений в реальном времени и историей.
4. Реализовать модель прав: хост, со-ведущий (editor), зритель (viewer).
5. Покрыть бизнес-логику и WebSocket-протокол тестами.

### 3.2. Вне границ проекта (на текущем этапе)

- Загрузка и хранение видеофайлов, транскодирование, стриминг (используются
  внешние источники: прямые ссылки на медиафайлы, YouTube/Vimeo-embed).
- Голосовой и видеозвонок внутри комнаты.
- Мобильные и настольные приложения.
- Платежи, реклама, монетизация.

## 4. Роли пользователей

| Роль | Возможности |
| --- | --- |
| Гость (неавторизованный) | Может войти в комнату по ссылке, если комната публичная, под выбранным ником; читает чат и получает состояние плеера |
| Участник (viewer) | Всё, что гость, плюс отправка сообщений в чат |
| Со-ведущий (editor) | Всё, что участник, плюс управление воспроизведением (play/pause/seek/rate) |
| Хост (host) | Всё, что editor, плюс смена источника видео, выдача и отзыв прав editor, кик участников, закрытие комнаты |

Правила:

- Создатель комнаты автоматически становится хостом.
- Хост может назначить несколько editor-ов одновременно (режим «совместное управление»).
- В MVP-режиме (`ROOM_CONTROL_MODE=host_only`) управлять воспроизведением может
  только хост; конфигурация переключается без изменения кода.
- При выходе хоста комната не закрывается сразу: хост передаётся первому
  присоединившемуся editor-у, иначе — старейшему участнику; если участников не
  осталось, комната живёт ещё `ROOM_TTL_MINUTES` и затем удаляется.

## 5. Пользовательские сценарии (user stories)

1. **Создание комнаты.** Пользователь регистрируется или входит как гость,
   создаёт комнату, указывает название и ссылку на видео, получает короткий
   инвайт-код и share-ссылку вида `/r/{invite_code}`.
2. **Присоединение.** Второй пользователь открывает ссылку, вводит ник (если гость),
   попадает в комнату, получает текущее состояние плеера и историю чата.
3. **Синхронный просмотр.** Хост нажимает «play» — у всех участников видео
   начинает воспроизводиться с одной и той же позиции (с учётом задержки сети).
4. **Перемотка.** Хост перематывает на 10:00 — у всех участников плеер
   переходит на 10:00 в течение 1 секунды.
5. **Чат.** Участник отправляет сообщение — оно появляется у всех присутствующих
   и сохраняется в истории.
6. **Смена прав.** Хост выдаёт право управления участнику; теперь оба могут
   ставить паузу.
7. **Восстановление соединения.** У участника пропал интернет на 30 секунд;
   после переподключения клиент запрашивает актуальное состояние и выравнивает
   позицию.
8. **Закрытие комнаты.** Хост завершает просмотр; все участники получают
   уведомление, комната помечается закрытой и недоступна для входа.

## 6. Функциональные требования

### 6.1. Аутентификация и пользователи (FR-1)

- FR-1.1. Регистрация по e-mail + пароль, уникальность e-mail и username.
- FR-1.2. Вход по e-mail + пароль, выдача пары JWT (access + refresh).
- FR-1.3. Обновление access-токена по refresh-токену, отзыв refresh-токена при выходе.
- FR-1.4. Гостевой вход: выдача временного токена, привязанного к комнате
  и нику (без записи в таблицу `users`).
- FR-1.5. Пароли хранятся только в виде хеша (bcrypt/argon2), минимальная длина — 8 символов.

### 6.2. Комнаты (FR-2)

- FR-2.1. Создание комнаты авторизованным пользователем или гостем.
- FR-2.2. Комната имеет уникальный `invite_code` (8 символов, base32-алфавит без
  похожих символов), устойчивый к перебору.
- FR-2.3. Приватность: `public` (вход по коду) и `private` (вход по коду + пароль комнаты).
- FR-2.4. Источник видео задаётся одним из способов: прямой URL медиафайла,
  embed-URL видеохостинга (YouTube/Vimeo) или `video_id` + `provider`.
- FR-2.5. Хост может сменить источник видео; смена сбрасывает позицию на 0
  и рассылается всем участникам.
- FR-2.6. Ограничение числа участников (`max_members`, по умолчанию 20).
- FR-2.7. Комната автоматически закрывается после `ROOM_TTL_MINUTES` без
  активности (нет подключённых участников) — реализуется фоновой задачей.
- FR-2.8. Список участников с ролями и статусом онлайн доступен всем в комнате.

### 6.3. Синхронизация воспроизведения (FR-3)

- FR-3.1. Состояние плеера: `is_playing`, `position_sec`, `playback_rate`,
  `updated_at` (серверное время), `updated_by`.
- FR-3.2. Управляющие команды: `play`, `pause`, `seek`, `set_rate`.
- FR-3.3. Команда от host/editor валидируется по правам, применяется к
  серверному состоянию и рассылается всем участникам, включая отправителя
  (единый источник истины — сервер).
- FR-3.4. Клиент вычисляет актуальную позицию как
  `position_sec + playback_rate * (now - updated_at)` при `is_playing = true`.
- FR-3.5. Сервер периодически (раз в 5 секунд) рассылает heartbeat состояния
  для компенсации дрейфа.
- FR-3.6. Клиент может отправить `sync.report` со своей текущей позицией;
  при расхождении больше `SYNC_DRIFT_THRESHOLD_SEC` (0.7 с) сервер отправляет
  этому клиенту персональную коррекцию.
- FR-3.7. Клиенты синхронизируют часы с сервером через `sync.ping`/`sync.pong`
  (измерение RTT, оценка смещения).

### 6.4. Чат (FR-4)

- FR-4.1. Отправка текстового сообщения (1–1000 символов) любым участником комнаты.
- FR-4.2. Сообщение доставляется всем подключённым участникам в реальном времени.
- FR-4.3. История сообщений хранится в БД и доступна с постраничной загрузкой
  (курсор по `created_at`/`id`), последние 50 сообщений отдаются при входе.
- FR-4.4. Системные сообщения о событиях комнаты (вход, выход, смена ролей,
  смена видео) помечаются типом `system`.
- FR-4.5. Хост может удалять сообщения (soft delete, пометка `deleted_at`).
- FR-4.6. Rate limiting: не более 5 сообщений в 2 секунды от одного участника.

### 6.5. Модерация и права (FR-5)

- FR-5.1. Выдача/отзыв роли `editor` хостом.
- FR-5.2. Кик участника хостом; кикнутый получает событие и отключается,
  повторный вход блокируется до конца жизни комнаты.
- FR-5.3. Передача роли хоста другому участнику.
- FR-5.4. Все изменения прав рассылаются всем участникам.

## 7. Нефункциональные требования

- **Производительность.** Задержка доставки события одному клиенту — не более
  200 мс при RTT до 100 мс. Один экземпляр сервера держит 500 комнат по 20
  участников (≈10 000 WebSocket-соединений) на 2 vCPU / 4 ГБ.
- **Надёжность.** Разрыв соединения не приводит к потере состояния; клиент
  восстанавливает его по `room.state` после reconnect. Сервер не хранит
  критичное состояние только в памяти.
- **Масштабирование.** Stateless HTTP-слой; горизонтальное масштабирование
  WebSocket обеспечивается через Redis Pub/Sub (этап v2, в MVP — один инстанс).
- **Безопасность.** JWT, хеширование паролей, валидация источника видео
  (защита от SSRF и `javascript:`-ссылок), CORS allow-list, ограничение
  размера сообщений и частоты запросов.
- **Наблюдаемость.** Структурированные логи (JSON), request-id, метрики
  количества комнат/соединений, health-check `/health`.
- **Совместимость.** Python 3.11+, PostgreSQL 15+; конфигурация через `.env`.
- **Документируемость.** OpenAPI/Swagger из FastAPI, описание WS-протокола в
  отдельном документе.

## 8. Архитектура

### 8.1. Общая схема

```
Клиент (браузер, плеер)
   │  HTTPS (REST)          WSS (WebSocket)
   ▼                          ▼
FastAPI (Uvicorn, asyncio)
   ├── api/v1        — REST-роутеры, схемы Pydantic
   ├── ws            — менеджер соединений, комнатный реестр, обработчики событий
   ├── services      — бизнес-логика (комнаты, права, воспроизведение, чат)
   ├── repositories  — доступ к данным (SQLAlchemy 2.0 async)
   ├── models        — ORM-модели
   └── core          — конфиг, безопасность, логирование, исключения
   │
   ▼
PostgreSQL  (пользователи, комнаты, участники, сообщения, состояние плеера)
```

Слои разделены: роутеры не работают с БД напрямую, сервисы не знают про HTTP,
ORM-модели не отдаются наружу (наружу — Pydantic-схемы).

### 8.2. Реестр соединений

`ConnectionManager` держит `dict[room_id, RoomSession]`, где `RoomSession` —
набор WebSocket-соединений с метаданными участника (user_id, guest_id, role).
Все операции над комнатой внутри процесса сериализуются через `asyncio.Lock`
на комнату, чтобы избежать гонок при одновременных командах play/seek.
Рассылка выполняет `asyncio.gather` с обработкой отвалившихся соединений;
«медленные» клиенты отключаются по таймауту записи.

## 10. WebSocket-протокол

Endpoint: `wss://{host}/api/v1/ws/rooms/{invite_code}?token={jwt}`

Жизненный цикл:

1. Клиент подключается с валидным токеном; сервер проверяет доступ к комнате.
2. Сервер отправляет `room.state` (участники, роль клиента, видео, состояние плеера)
   и `chat.history` (последние 50 сообщений).
3. Сервер рассылает остальным `presence.joined`.
4. Далее — обмен событиями; сервер отвечает на `sync.ping`.
5. При разрыве сервер рассылает `presence.left`; клиент переподключается
   с экспоненциальной задержкой (1→2→4→8 с, максимум 5 попыток).

Все сообщения — JSON-объекты вида `{"type": "...", "data": {...}, "ts": <server_ms>}`.

### 10.1. Клиент → сервер

| Тип | data | Права |
| --- | --- | --- |
| `playback.play` | `position_sec` | host / editor |
| `playback.pause` | `position_sec` | host / editor |
| `playback.seek` | `position_sec` | host / editor |
| `playback.set_rate` | `rate` (0.25–2.0) | host / editor |
| `chat.send` | `text`, `client_msg_id` | участник |
| `sync.ping` | `client_ts` | участник |
| `sync.report` | `position_sec`, `is_playing` | участник |
| `room.leave` | — | участник |

### 10.2. Сервер → клиент

| Тип | data | Когда |
| --- | --- | --- |
| `room.state` | комната, участники, роль, видео, состояние плеера | при подключении |
| `room.closed` | `reason` | комната закрыта хостом или по TTL |
| `playback.state` | `is_playing`, `position_sec`, `playback_rate`, `updated_at`, `updated_by` | на любую команду и heartbeat раз в 5 с |
| `sync.pong` | `client_ts`, `server_ts` | ответ на ping |
| `sync.correction` | `position_sec`, `playback_rate`, `server_ts` | при расхождении > порога |
| `chat.message` | `id`, `author`, `text`, `created_at`, `client_msg_id` | новое сообщение |
| `chat.deleted` | `message_id` | сообщение удалено |
| `presence.joined` / `presence.left` | `member` | вход/выход участника |
| `member.updated` | `member` (роль изменилась) | смена прав |
| `video.changed` | `video_source` | смена видео хостом |
| `error` | `code`, `message`, `details?` | ошибка обработки события |

### 10.3. Идемпотентность и порядок

- `client_msg_id` (UUID) позволяет клиенту отбросить дубли при ретрае.
- Каждое изменение состояния имеет монотонный `revision`; клиент игнорирует
  `playback.state` с `revision` меньше уже применённого (защита от переупорядочивания).
- Невалидные события не разрывают соединение: сервер отвечает `error` с кодом.

## 11. Ошибки

Единый формат:

```json
{ "error": { "code": "ROOM_NOT_FOUND", "message": "Комната не найдена", "details": {} } }
```

| HTTP | Код | Ситуация |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Некорректное тело запроса |
| 401 | `UNAUTHORIZED` / `TOKEN_EXPIRED` | Нет/просрочен токен |
| 403 | `FORBIDDEN` / `NOT_ROOM_ADMIN` | Недостаточно прав |
| 404 | `ROOM_NOT_FOUND` / `MESSAGE_NOT_FOUND` | Объект не найден |
| 409 | `ROOM_FULL` / `ALREADY_JOINED` / `ROOM_CLOSED` | Конфликт состояния |
| 422 | `INVALID_VIDEO_SOURCE` | Ссылка не прошла валидацию |
| 429 | `RATE_LIMITED` | Превышен лимит запросов |
| 500 | `INTERNAL_ERROR` | Необработанная ошибка |

WS-ошибки используют те же `code` внутри события `error`.

## 12. Модель данных

```
users(id uuid PK, email unique, username unique, password_hash, created_at, is_active)
rooms(id uuid PK, invite_code unique, name, host_id FK->users NULL,
      visibility enum, password_hash NULL, video_provider, video_url, video_id NULL,
      max_members, status enum(active|closed), created_at, closed_at NULL)
room_members(id uuid PK, room_id FK, user_id FK NULL, guest_id NULL, nickname,
      role enum(host|editor|viewer), is_kicked bool, joined_at, last_seen_at,
      UNIQUE(room_id, user_id), UNIQUE(room_id, guest_id))
playback_state(room_id PK FK->rooms, is_playing bool, position_sec float,
      playback_rate float, revision bigint, updated_by FK->room_members,
      updated_at timestamptz)
messages(id uuid PK, room_id FK, author_member_id FK->room_members,
      type enum(user|system), text, client_msg_id NULL, created_at, deleted_at NULL)
refresh_tokens(id uuid PK, user_id FK, token_hash, expires_at, revoked_at NULL)
```

Индексы: `rooms(invite_code)`, `room_members(room_id)`, `messages(room_id, created_at DESC)`,
`messages(room_id, client_msg_id)` (частичный уникальный для идемпотентности).

Миграции — Alembic. Состояние плеера хранится в БД, чтобы переживать рестарт
и переиспользоваться при повторном входе.

## 14. Тестирование (Pytest)

- `pytest-asyncio` (`asyncio_mode=auto`), `httpx.AsyncClient` + `ASGITransport`
  для REST-тестов без поднятия сети.
- Интеграционные тесты — на реальном PostgreSQL (фикстура создаёт схему и
  откатывает транзакцию после каждого теста; в CI — сервис-контейнер).
- WebSocket-тесты — через `TestClient.websocket_connect`: проверяются
  handshake, авторизация, рассылка, права, идемпотентность, heartbeat.
- Обязательные кейсы: гость не может управлять плеером; editor может после
  выдачи права; перемотка вне длительности отклоняется; вход в закрытую
  комнату — 409; превышение `max_members` — 409; reconnect возвращает
  актуальное состояние; расхождение позиции вызывает `sync.correction`.
- Целевое покрытие сервисного слоя — не ниже 80 %, overall — не ниже 70 %.
- `ruff` + `mypy` (strict для `services` и `ws`) в pre-commit и CI.

## 16. Риски и способы снижения

| Риск | Влияние | Снижение |
| --- | --- | --- |
| Дрейф позиции из-за разных задержек | Расхождение видео у участников | Единый источник истины на сервере, heartbeat, `sync.report` + коррекции |
| Гонки при одновременных командах | «Прыгающая» перемотка | `asyncio.Lock` на комнату, монотонный `revision` |
| Медленные/зависшие клиенты | Блокировка рассылки | Таймаут записи, отключение медленных, `gather` с `return_exceptions` |
| Масштабирование WebSocket за пределы одного инстанса | Ограничение нагрузки | Абстракция брокера, план перехода на Redis Pub/Sub |
| Небезопасные URL видео (SSRF, XSS) | Уязвимость | Allow-list схем и доменов, санитизация |
| Разрастание объёма чата | Замедление запросов | Курсорная пагинация, индексы, retention |
